Built 2026-08-04 per a brief from the tech lead. Backend (`ApplicantController`, routes) already existed — this was frontend-only (Blade + inline vanilla JS), no controllers/routes/JS modules touched. See [[spa-page-conventions]] for the general SPA patterns these follow.

Files:
- `resources/views/pages/recruitment/applicant_new.blade.php` — add-applicant form. Loads `GET /api/applicants/formConfig` (`{form, locations:[{id,name}], fields:[{id,field_key,label,type,options,is_required,order,file_rules,help_text}]}`), renders Candidate Name + read-only Date + Preferred Location + dynamic fields (text/number/textarea/date/select/radio/checkbox/file) keyed by `data-field-key`/`data-field-type` containers. Submits `FormData` to `POST /api/applicants` (`full_name`, `location_id`, `form_data[key]`/`form_data[key][]`, `files[key]`).
- `resources/views/pages/recruitment/applicants.blade.php` — list. Uses `<x-table id="applicantsTable">` + `renderRemoteTable` against `GET /api/applicants` (Laravel paginator). Status filter (`#applicantStatusFilter`) → `table.setFilter('status', ...)`. Team-leader-only scope toggle (`#scopeAllToggle`, gated by `@if(auth()->user()->is_team_leader)`) → `table.setFilter('scope', 'team'|'mine')`. Row click → `loadPage` to `applicant_view`.
- `resources/views/pages/recruitment/applicant_view.blade.php` — detail. Root `<div id="applicantDetailRoot" data-applicant-id="{{ $applicantId }}">`. Loads `GET /api/applicants/{id}` → `{id, full_name, status, created_at, last_activity_at, form_version, location_name, assignee_name, team_name, answers:[{field_key,label,type,value,options}], files:[{id,field_key,original_name,url}], checklist:[{id,checklist_item_id,label,order,is_done,done_at,done_by,done_by_name}]}`. Status `<select>` → `PATCH /api/applicants/{id}/status` `{status}`, response is `{status, checklist}` (NOT the full applicant — controller only returns those two keys), used to re-render badge + checklist panel. Checklist checkboxes → `PATCH /api/applicants/{id}/checklist/{itemId}` `{is_done}`, response is the single updated checklist item row.

Status badge color map used consistently across list + detail (STATUS_BADGES const): New=zinc, In Review=blue, Interview=amber, Offer=purple, Hired=green, Rejected=red, each with a dark-mode variant.

Not verified in a browser (no tool access) — only confirmed via `php artisan tinker` rendering each Blade file directly (`view()->file(...)->render()`) with no compile/runtime errors, and `php -l` syntax checks.

**2026-08-05 update** (per a second brief): `applicants.blade.php` reworked significantly — Add modal is now a lightweight create (`full_name` + optional `role_id`/`source_id`/`location_id`/`phone`/`email`/`date_of_birth`/`notes`, plain JSON POST, no more FormData/dynamic fields in that modal). The 33 dynamic form fields moved to a new `interviewApplicantSideModal` (`#interviewFieldsContainer`, `#submitInterviewBtn`) reached via a `#btnInterview` button in the View modal; submitting opens a centered `interviewOutcomeModal` (Pass/Fail/Cancel) which PATCHes multipart FormData (`isJson:false`) to `/api/applicants/{id}/interview` with `outcome=pass|fail` appended — confirmed `apiCall` supports PATCH+FormData natively (no method-spoofing needed, see [[spa-page-conventions]]). View modal widened via scoped `<style>` override on `#viewApplicantSideModal .side-modal-panel` (shared `side-modal.blade.php` component left untouched), relaid out 2-column, dropped the Team field, and gained: Interview Summary textarea+save (`PATCH .../interviewSummary`), Notes (append-only, `GET/POST .../notes`), a Copy-answers button (clipboard), and orientation scheduling (`btnScheduleOrientation` visible only when `status==='Orientation'`, opens centered `orientationModal`, `PUT .../orientation`). New `Orientation` entry added to `STATUS_BADGES` (teal). `app_settings.blade.php`'s checklist-group "Target status" field changed from free-text input to a `<select>` populated from `/api/lookupLists` (the list with `key==='status'`, active top-level items only), cached on first open in `statusLookupItems`.

Gotcha confirmed while doing this: `window.clearInputs()` (called by `closeSideModal` in `customFunctions.js`) clears **every** input/select/textarea on the whole page, not just the modal being closed — a pre-existing global side effect, not fixed (out of scope), but worth remembering if a future brief reports "my other modal's fields got wiped" after closing an unrelated side-modal.

**2026-08-06 update** (per a third, frontend-only brief; backend already shipped territory/location, activity log, edit-info/edit-answers, and export endpoints — see [[spa-page-conventions]] for the export/customConfirm/date-input notes): `applicants.blade.php` and `orientation_schedule.blade.php` reworked further:
- Territory/location is now two-level (`lookup_list_items.parent_id`: top-level = Territory, children = Location). Added shared helpers `populateTerritorySelect(el, territories)` / `populateLocationSelect(el, territory)` plus a page-level `cachedTerritories` (and `cachedRoles`, mirroring the existing `cachedSources`), all filled from `/api/applicants/formConfig`'s `territories:[{id,name,locations:[{id,name}]}]`.
- Add Applicant modal dropped Preferred Location entirely (removed `#locationSelect` + old `renderLocations()`) — location capture now only happens via Interview/Edit-Info.
- View modal gained `#btnEditInfo` (header) opening a new `editApplicantSideModal` (mirrors Add-modal field styling + a territory/location row) that PATCHes `/api/applicants/{id}/info` with full-payload JSON (every key sent, `null` for empty — endpoint leaves omitted keys unchanged, so omission is unsafe here). `date_of_birth` prefill is lossy: `show()` only returns a pre-formatted string, so the edit form does a best-effort `new Date(friendlyString)` parse (local date parts, not `toISOString`) and leaves the input blank if unparseable.
- View modal also gained `#btnEditAnswers` (Answers card, visible only when `applicant.has_answers`) and an Activity History card (`#activityList`, `GET /api/applicants/{id}/activity`, rendered newest-first as the API already sorts it, loaded alongside notes in `loadApplicant()`).
- The Interview side-modal (`interviewApplicantSideModal`) is now dual-mode via a module-scoped `interviewMode` ('interview' | 'edit'), both driven through the same `renderInterviewFields(fields, {includeTerritoryLocation})`/`submitInterviewBtn` — 'interview' mode prepends a JS-rendered territory/location row (`#interviewTerritorySelect`/`#interviewLocationSelect`, ids only exist after render since they're template-literal HTML, not static Blade) and POSTs to `/interview` (multipart+spoofed PATCH) with `outcome`+`territory_id`+`location_id`; 'edit' mode (opened via `#btnEditAnswers` → `openEditAnswersModal()`) renders fields only (no territory row) and POSTs to `/answers` instead. Required-field validation failure on the interview path now shows a `customConfirm` ("...will be marked Rejected") instead of just blocking — accepting submits `incomplete=1`+territory/location only (no `form_data`/`files`/`outcome`) via a new `submitIncompleteInterview()`.
- Both pages gained an Export button → a centered `<x-modal>` (`exportModal` / `orientationExportModal`) with format select + From/To date inputs + Today/This-Week/Last-Week presets, driving `window.location.href` to `/api/applicants/export` or `/api/applicantOrientations/export` (binary download, not `apiCall` — see [[spa-page-conventions]]). Scope resolved from the existing `#scopeAllToggle` (unchecked → `mine`, else `team`).
- Not verified in a browser — only `node --check` on the extracted `<script>` body of each file (no compile errors) and `Grep` id-uniqueness checks for every new DOM id.
